# ADR-0005: Optimistic concurrency и audit

- **Статус:** Accepted
- **Дата:** 2026-09-27
- **Участники:** команда К.У.М.

## Контекст

Несколько пользователей могут одновременно редактировать модели и структуру миров. Нужны предсказуемые конфликты без «тихой» потери данных и полный след изменений для расследований и compliance.

## Решение

1. **Optimistic concurrency**
   - у мутируемых агрегатов есть версия (`version` / `etag`);
   - команда изменения передаёт ожидаемую версию;
   - при несовпадении — конфликт (HTTP 409 или эквивалент), без автослияния сервером по умолчанию.

2. **Audit**
   - каждое успешное мутирующее действие пишет `AuditEvent` (кто, когда, что, before/after или diff, correlation id);
   - audit append-only; удаление/правка аудита недоступны обычному API;
   - симуляции и структурные изменения миров аудируются обязательно.

## Последствия

**Плюсы**

- Нет скрытых overwrite.
- Прозрачность истории изменений.

**Минусы / риски**

- Клиент должен уметь показывать конфликт и предлагать refresh/reapply.
- Объём audit-хранилища растёт — нужна политика retention (отдельное решение позже).

**Следствия для реализации**

- Контракты команд включают `expectedVersion`.
- Интеграционные тесты на race и на наличие audit-записи.
